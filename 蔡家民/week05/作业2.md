# 作业2：本地 Ollama 运行 qwen3-0.6b + OpenAI SDK 调用

## 一、原理：为什么 OpenAI SDK 能调本地模型

Ollama 除了自己的原生 API（`/api/generate`、`/api/chat`），还内置了一层 **OpenAI 兼容接口**，挂在 `/v1` 路径下。所以 openai 官方 SDK 不需要任何改造就能访问本地模型，只改两个参数：

| 参数 | 云端 OpenAI | 本地 Ollama |
|------|------------|-------------|
| `base_url` | `https://api.openai.com/v1` | `http://localhost:11434/v1` |
| `api_key` | 真实密钥 | 任意非空字符串（不校验） |

`api_key` 必须传值，但内容随便填。填空字符串不行——SDK 自己会在客户端就抛错，请求根本发不出去。

这个设计的实际价值：业务代码统一用 OpenAI 接口，开发阶段接本地小模型省钱省网，上线只改配置就能切云端 API。

## 二、环境准备

### 1. 安装 Ollama

Windows 直接从 [ollama.com/download](https://ollama.com/download) 下安装包，装完服务会自动后台常驻。验证：

```bash
ollama --version          # ollama version is 0.32.13
curl http://localhost:11434/api/tags   # 返回 JSON 说明服务活着
```

### 2. 拉取模型

```bash
ollama pull qwen3:0.6b
```

实际下载 522MB（Q4_K_M 量化的 GGUF 文件）。**速度只有 87KB/s ~ 200KB/s，花了约 20 分钟。**

国内慢是因为 ollama registry 没有境内节点，但能连通，**不用开代理**。如果以后要下 7B/14B 这种大模型，建议开代理，或者从 ModelScope 下 GGUF 再用 `ollama create` 导入。

### 3. 安装 SDK

```bash
pip install openai        # 本次装的是 2.46.0
```

本机装在 conda 环境 `py312`（Python 3.12.13）。

### 4. 模型信息

`/api/tags` 返回的元数据：

```
parameter_size:     751.63M      实际参数量，比名字里的 0.6B 略高
quantization_level: Q4_K_M       4bit 量化，磁盘占用 522MB
context_length:     40960        上下文窗口 40K
embedding_length:   1024         隐层维度
capabilities:       completion, tools, thinking
```

`tools` 表示支持 function calling，`thinking` 表示支持思考模式。这两个能力在 0.6B 规模下都不太可靠，但接口层面是通的。

## 三、代码实现

`ollama_openai_sdk.py` 分四个函数，各演示一个知识点：

### 1. `chat_once()` — 基础调用

作业给的原始代码，额外打印了 `response.usage`。本地模型同样会返回 token 统计。

### 2. `chat_stream()` — 流式输出

`stream=True` 后返回值从完整对象变成迭代器，每次取 `chunk.choices[0].delta.content`。**必须判空**，因为首个 chunk 通常只带 `role` 不带内容。

### 3. `chat_multi_turn()` — 多轮对话

最容易踩坑的地方：**模型是无状态的**，服务端不保存任何历史。要让模型"记住"上文，必须每轮把完整 `messages` 列表重新发过去，并且把模型自己的回复也用 `{"role": "assistant", ...}` 追加进历史。

```python
messages.append({"role": "user", "content": q})
answer = client.chat.completions.create(...).choices[0].message.content
messages.append({"role": "assistant", "content": answer})   # 关键这一步
```

### 4. `list_models()` — 连通性检查

`client.models.list()` 是最轻量的健康探测，比发一次对话快得多，适合放在程序启动时。

## 五、遇到的问题

### Windows 控制台编码报错

第一次运行在 `print()` 处崩了：

```
UnicodeEncodeError: 'gbk' codec can't encode character '\U0001f60a' in position 14
```

模型输出里带了 emoji（😊），而 Windows 控制台默认 GBK 编码装不下。

**注意这不是 API 调用失败**——请求早就成功返回了，纯粹是打印环节的问题。修法是在脚本开头加一行：

```python
sys.stdout.reconfigure(encoding="utf-8", errors="replace")
```

写在代码里比设环境变量 `PYTHONIOENCODING=utf-8` 好，因为脚本能独立运行、换机器也不用额外配置。这个坑在 Windows 上跑任何 LLM 代码都会碰到。

### token 数和可见输出对不上

第 1 部分 `completion=134`，但可见文字只有十几个字。差额是 qwen3 默认开启的思考过程（`<think>` 段）——兼容层把它算进了 completion token，但没体现在 `message.content` 里。

想关掉思考模式省 token：

```python
extra_body={"chat_template_kwargs": {"enable_thinking": False}}
```

### 模型能力局限

多轮对话第二轮，模型把"我叫蔡家民"理解成了自我介绍，回了"你好，我是蔡家民"。历史传递机制是生效的（它确实取到了名字），但指代和意图理解出了偏差。

这属于 0.6B 参数规模的正常局限，不是代码问题。要更好的效果可以换 `qwen3:1.7b` 或 `qwen3:4b`。

```bash
ollama pull qwen3:0.6b
pip install openai
python ollama_openai_sdk.py
```
