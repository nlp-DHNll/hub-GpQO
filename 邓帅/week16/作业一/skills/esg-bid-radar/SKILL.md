# ESG 招投标情报

## 概览

两种模式。**汇总模式**：汇总时间窗内（默认近 24 个月）ESG 相关的中标情况，分析热点招标主题与中标金额分布。
**监控模式**：只找基线日之后新发布的招标公告，出一份日报，并更新已见清单。

核心原则：**样本不是全量——报告里的每个数字都能回到公告原文；取不到的金额写 null，不估、不编；边界外的招标只进附录、不进统计。**

## 何时触发

使用者点名了本 skill，或者要「汇总 / 分析 ESG、双碳相关的招标、中标情况」，或者要「盯 / 监控 / 每天看新的 ESG 招标」。

先判断模式，再动手：

- 请求里有「过去两年 / 近 N 个月 / 汇总 / 中标情况 / 热点 / 金额分布 / 趋势」→ **汇总模式**。
- 请求里有「监控 / 每天 / 新增 / 新招标 / 日报 / 今天有哪些」→ **监控模式**。
- 两种都要（先汇总、再开始监控）→ 分两次运行，先汇总。

ESG 月报不归本 skill（用 esg-monthly-report）。

## 参数

| 参数 | 汇总模式 | 监控模式 |
|---|---|---|
| 时间窗 | 成文日前 24 个月 | 基线日至今天；基线日默认取上一次运行的日期，首次运行取 7 天前 |
| 搜索预算 | 40 次（`web_search_prime` 的调用上限，读页不计） | 20 次 |
| 样本目标 | 范围内中标公告不少于 60 条 | 不设 |
| 已见清单 | 不用 | `runs/seen/esg-bid-radar.json` |

请求里显式给出的值优先于默认值。无头运行的提示词若给出了时间窗，以提示词为准——监控模式下时间窗的起始日就是基线日。
实际使用的时间窗、样本量写在报告开头。

## 范围规则

「ESG 相关招标」指采购内容属于 ESG/双碳**专业服务**的招标，分六类，这六类也是主题标签的取值：

| 主题标签 | 典型采购内容 | 检索词（任选组合） |
|---|---|---|
| 咨询规划 | 碳达峰碳中和路径研究、双碳规划、ESG 战略咨询 | 双碳咨询、碳达峰路径、碳中和规划 |
| 碳排放核算与核查 | 温室气体核算、碳核查、碳盘查、排放清单编制 | 碳排放核算、碳核查、温室气体清单 |
| 报告编制与鉴证 | ESG/可持续发展报告编制、ESG 鉴证、TCFD/ISSB 披露 | ESG报告编制、可持续发展报告、ESG鉴证 |
| 碳资产管理与交易 | 碳资产开发、CCER 项目、碳配额管理、碳交易服务 | 碳资产管理、CCER开发、碳交易服务 |
| 双碳平台与监测系统 | 双碳/能碳管理平台的建设与运维、碳排放监测系统 | 双碳平台、能碳管理平台、碳排放监测系统 |
| 培训认证 | 碳排放管理员培训、碳交易员培训、ESG 相关认证 | 碳排放管理培训、碳交易培训 |

**边界外**：与 ESG 沾边、但买的不是专业服务的招标——环保工程、节能改造施工、新能源建设、设备与货物采购、检测仪器采购。
边界外的记录 `in_scope` 写 `false`，`topic` 自由填写（如「环保工程」「设备采购」），只进附录，不进任何统计。

判断方法：看「采购内容」的主体是什么。买的是服务与智力成果（方案、核算、报告、平台的开发服务、培训）算范围内；
买的是工程、货物、设备算边界外。软硬件打包的「双碳管理平台」，平台开发服务占主要金额才算范围内。
拿不准的从保守：不算进样本，放进附录并写明理由。

## 检索工具约定

| 用途 | 工具 | 约定 |
|---|---|---|
| 搜索 | `web_search_prime`（智谱搜索） | 主用。`location` 设 `cn`；`content_size` 用 `medium`。`search_domain_filter` 可把检索限定到政府采购、公共资源交易类站点。 |
| 读原文 | `webReader`（智谱读页） | 每条拟采用的公告都要读原文：金额、采购人、发布日期以原文为准。 |
| 补充搜索 | `WebSearch`（内置网页搜索） | 只在智谱搜索没有结果时补充；结果多是跳转链接，须读原文核对。 |
| 网页抓取 | `WebFetch`（内置网页抓取） | 禁用：对中国域名不可用。 |

读页工具抓不了带中文编码参数的地址（链接里出现 `%` 编码的中文时返回 -400）。遇到这种地址，按顺序试：
换同一公告的另一个来源（官方站点、可读的转载页）；从搜索结果里取该站点的可访问链接重搜；都读不到就只用搜索摘要，
把它登记为「仅见摘要」，金额写 `null`。不要自己拼接或解码地址。

**子代理**：默认由你自己完成。预算接近上限或矩阵很大时，可以派子代理分担检索，同时运行的不超过 3 个；
每个子代理负责矩阵中的一部分，回传候选公告的链接，由你统一读原文、登记记录。

## 查询矩阵

### 汇总模式：主题词 × 公告类型 × 时间段

时间过滤只有近一年（`oneYear`）和不限（`noLimit`）两档能覆盖 24 个月，是否落在时间窗内由你逐条读发布日期判断。

| 维度 | 取值 |
|---|---|
| 主题词 | 上表六类各一组中文检索词；另加 `ESG报告 鉴证`、`可持续发展报告 编制` 两个同义写法 |
| 公告类型 | 中标公告为主（统计对象）；招标公告为辅（看热度，不进样本） |
| 时间段 | `oneYear` 与 `noLimit` 各一轮 |

预算 40 次时的分配：六类主题 × 中标公告 × 两轮时间段 = 12 次；六类主题 × 招标公告 × `oneYear` = 6 次；
两个同义写法各 2 次；限定到政府采购与公共资源交易站点的检索 6–8 次；其余留给换词补搜。
每条检索词后面带上「中标公告」「采购」「招标」这类词，比只写主题词准。检索词宁短勿长：2–4 个词就够了，
堆到六七个词搜索引擎几乎召回不到东西（「ESG报告编制 鉴证服务 中标公告」不如「ESG报告 中标」）。
`search_domain_filter` 常常不生效；想限定站点，就把站点名写进检索词（如「碳排放核算 中标公告 中国政府采购网」）。

**小预算运行**（请求写明了更小的搜索预算）：六类主题每类至少 1 次中标公告检索，再做 3–4 次站点限定检索；
在「方法与来源说明」写明实际次数与没有覆盖到的主题。

**换词补搜**：某一类主题一条范围内中标公告都没找到时，换同义词（见上表第三列）、去掉站点限定再搜一次；
仍然没有，就在报告里如实写「该主题本期未检索到样本」。

### 监控模式：主题词 × 时间过滤

六类主题各一次「主题词 + 招标公告 / 采购公告」，时间过滤用 `oneWeek`；结果太少（不足 10 条）的那一类改用 `oneMonth` 再搜一次；
另做 2–3 次限定到中国政府采购网等站点的检索。候选公告逐条看发布日期，只留严格晚于基线日的。

## 逐条登记的规则

每条公告登记成一条招标记录，十三个字段的含义与样例见 `references/产物格式.md`。容易出错的几项：

**公告类型**（`notice_type`）：标题或正文写「中标公告 / 成交公告 / 中标结果」→ `award`；
「招标公告 / 采购公告 / 竞争性磋商 / 竞争性谈判 / 询价公告 / 单一来源公示」→ `tender`；更正、答疑、废标、终止 → `other`。

**发布日期**（`published_at`）：以公告页面上的发布日期为准，统一写成 `YYYY-MM-DD`；搜索引擎标注的「N 天前」是索引时间，不是发布日期。
页面不显示日期就写 `null`（监控模式下发布日期取不到的公告不进日报）。

**中标金额**：必须打开公告原文才能填，`amount_text` 照抄原文写法，`amount` 换算成元。

| 原文写法 | `amount_text` | `amount` |
|---|---|---|
| 190万元 | 190万元 | 1900000 |
| 1.2亿元 | 1.2亿元 | 120000000 |
| 人民币壹佰玖拾万元整 | 人民币壹佰玖拾万元整 | 1900000 |
| 86.5万元（按收费标准下浮 5%） | 86.5万元（按收费标准下浮 5%） | 865000 |
| 按国家收费标准下浮 20% | 按国家收费标准下浮 20% | null |
| 80万元至100万元 | 80万元至100万元 | null |
| 预算金额：120万元 | null | null |

折扣率、区间、单价换算不出一个确定金额的，`amount` 写 `null`；预算金额、最高限价不是中标金额。分标段、分多包的公告，合计金额明确写出才取合计，否则写 `null`。

**采购人**（`purchaser`）：招标公告里的「采购人」或「招标人」，写全称。
**地区**（`region`）：写到省级行政区（省、自治区、直辖市）；跨省的写主要实施地；取不到写 `null`。
**来源站点**（`source_site`）：公告所在站点的名称，如「中国政府采购网」「江苏省公共资源交易中心」「中国招标投标公共服务平台」。
**核实状态**（`verification`）：已核实（打开过原文并核对）、仅见摘要（只看到搜索摘要）、已排除（打开后发现不适用）。

**同一公告的多处转载**只登记一条，保留官方站点或最先发布的那个地址；标题与采购人都相同的多条结果视为同一条。

## 流程：汇总模式

1. 定参数，按「查询矩阵」列出检索词。
2. 逐条检索，汇总候选公告（去重后）。
3. 对拟采用的公告逐条读原文，登记招标记录；判不准范围的记下来，按「范围规则」从保守。
4. 达到样本目标或预算用完就停。样本目标没达到而预算还有余，就继续换词、换同义写法去找，不要提前收工；
   预算用完仍不足，就在「方法与来源说明」如实写明实际检索次数、样本量与来源构成。
5. 只在**范围内且是中标公告**的记录上做统计，按固定结构成文。
6. 写 `report.md` 与 `data.json`，按「写完后的自查」逐项过一遍。

统计口径（样本 = `in_scope` 为真且 `notice_type` 为 `award` 的记录）：

| 分析项 | 怎么算 |
|---|---|
| 热点主题排行 | 按主题标签统计样本数与中标金额合计；金额合计只用取到金额的样本，并注明合计覆盖几条 |
| 金额分布 | 100 万元以下 / 100 万（含）至 1000 万元 / 1000 万元（含）以上 三档，外加「金额不可得」一档 |
| 月度趋势 | 样本按发布年月计数；24 个月逐月列表太稀时按季度归并，标题写成「月度趋势（按季归并）」 |
| 采购人类型与地区分布 | 采购人类型分：政府部门、事业单位、国有企业、开发区/园区管委会、行业协会与社会组织、其它；地区按省级行政区 |
| 典型项目 | 5–8 条有代表性的样本（金额大、主题典型、地区分散），每条带链接 |
| 金额可得率 | `amount` 不为空的样本数 ÷ 样本量，写成 `80%（4/5）` |

金额单位在表格里用「万元 / 亿元」，数字来自 `data.json`，不要另算一套。

## 流程：监控模式

1. **先留快照**：读已见清单；文件不存在就当空清单（首次运行）。开始检索之前，把它原样复制为运行目录下的 `seen_before.json`
   （运行目录里已经有这个文件时不要覆盖）。已见清单不存在时，快照写 `{"records": []}`。
2. 按「查询矩阵」检索，收集候选公告。
3. 筛：只留**招标公告**（`tender`）且**发布日期严格晚于基线日**的。基线日当天的、发布日期取不到的、中标与更正类公告都不算新增。
4. 去重：去掉已在 `seen_before.json` 里的；同一公告的多处转载只留一条。
5. 逐条读原文，补齐采购人、截止日期（`deadline`，原文写法）与一句话摘要（`summary`）。
6. 写 `report.md` 与 `data.json`（每条在十三个字段之外还要有 `deadline` 与 `summary`）。没有新增也出一份日报。
7. **更新已见清单**：把本次新增的记录追加到清单末尾，旧的条目原样保留；清单文件不存在就新建 `{"records": [...]}`。

去重时链接的小差别不算不同链接：`http` 与 `https`、末尾有无斜杠、`#` 及其后的内容、`utm_` 开头的跟踪参数。
写进 `data.json` 与已见清单的链接用公告原始地址，正文里的链接与 `data.json` 里的一字不差。

**每日触发**（可选，默认不启用）：在 week16 下建一个 launchd/cron 任务，每天执行一次
`用 esg-bid-radar 监控今天新增的 ESG 相关招标，出一份日报`。见 `作业一/readme.md`「每日监控」。

## 三件产物

写到运行目录（无头运行由提示词给出；交互运行默认 `邓帅/week16/runs/<YYYYMMDD-HHMMSS>_bid-radar_noscript_<模式>/`）：

| 文件 | 内容 |
|---|---|
| `report.md` | 汇总报告或日报，骨架见 `references/产物格式.md` |
| `data.json` | 招标记录：`{"records": [...]}`。每条含 `title`、`url`、`notice_type`、`published_at`、`purchaser`、`region`、`topic`、`in_scope`、`amount`、`amount_text`、`winner`、`source_site`、`verification` 十三个字段，一个都不能少；取不到的写 `null`（`title`、`url`、`notice_type`、`in_scope`、`verification` 必填） |
| `run.json` | 运行记录。无头运行由运行器生成，不要自己写；交互运行按模板自己写 |
| `seen_before.json` | 仅监控模式：运行前已见清单的快照 |

## 写完后的自查

逐项过一遍，有问题就改完再结束：

1. 报告开头的声明与本次运行一致：汇总模式写时间窗、样本量、来源构成、金额可得率；监控模式写覆盖范围。
2. `data.json` 顶层是对象，每条十三个字段齐全；取值都是约定写法（`tender`/`award`/`other`、`verified`/`summary-only`/`excluded`）。
3. 汇总模式：五个分析项各有一节；每条边界外招标的链接都出现在附录里，且正文其它位置没有它们的链接；
   各项统计只用了范围内的中标公告，数字与 `data.json` 对得上。
4. 监控模式：每条都是招标公告、发布日期都严格晚于基线日、都不在 `seen_before.json` 里；
   每条的链接都在正文里；已见清单已追加本次新增。

## 常见错误

| 错误 | 后果 | 改法 |
|---|---|---|
| 把搜索摘要里的金额直接填进 `amount` | 金额没有原文依据，可能抄错 | 金额只从打开过的原文里取；读不到原文就写 `null` 并标「仅见摘要」 |
| 预算金额、最高限价当成中标金额 | 金额分布失真 | 只取「中标金额 / 成交金额」；没有就写 `null` |
| 边界外的招标进了统计 | 热点与金额被工程、设备类项目带偏 | 先判范围再做统计；边界外的只进附录 |
| 样本当全量汇报 | 结论说过头 | 开头与结论都写明「样本」、样本量与来源构成 |
| 监控日报里混进中标公告，或发布了基线日当天的公告 | 日报提醒的不是「将要采购」 | 只留 `tender` 且发布日期严格晚于基线日 |
| 第二次运行的日报重复了第一次的条目 | 使用者不再信任推送 | 先留快照、再去重；运行后把新增追加进已见清单 |
