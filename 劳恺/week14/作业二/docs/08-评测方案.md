## 1. 评测集构造

自建 **30 道题**，分四类。每题标注：标准答案所在文档、页码、是否必须看图、关键词。

| 类别 | 题数 | 说明 | 考察能力 |
|---|---|---|---|
| **A. 纯文本题** | 10 | 答案在 PDF 的正文文字里 | 基本 RAG 检索能力 |
| **B. 图问题（必须看图）** | 10 | 答案只存在于图里（图表数值、示意图结构、照片内容） | **多模态链路是否真的通了** |
| **C. 表格/公式题** | 5 | 答案在表格或公式里 | 版面解析质量、切块质量 |
| **D. 多轮题** | 5 | 依赖前文（"那张图的第二根柱子呢？"） | 会话历史、上下文管理 |

### 1.1 题目格式

```yaml
- id: B03
  question: "2024 年营收峰值出现在哪个季度？峰值是多少？"
  category: B            # 必须看图
  answer_docs: [d_ab12cd34ef56]
  answer_pages: [7]
  answer_images: [d_ab12cd34ef56_p7_i1]   # 正确引用应指向这张图
  keywords: ["42.3", "第三季度", "Q3"]
  requires_image: true
  notes: "答案数字 42.3 只出现在第 7 页的柱状图里，正文没有"
```

### 1.2 题目来源建议

- 用**真实业务 PDF**（财报、年报、产品手册、教材）→ 答案有明确出处，可自动生成关键词。
- B 类题必须**人工确认"文字里确实没有答案"**，否则无法证明多模态链路的价值。

## 2. 指标

### 2.1 检索层指标（自动）

| 指标 | 定义 | 目标 |
|---|---|---|
| **Hit@k** | 标注的正确 chunk 出现在 top-k 的比例 | k=8 时 ≥ 85% |
| **MRR** | 正确 chunk 排名的倒数均值 | ≥ 0.7 |
| **图片召回率** | 标注的正确图片出现在本次送模图片中的比例 | ≥ 80% |
| **引用准确率** | 模型输出的 `[[cite:...]]` 中，有多少指向了标注的正确图片 | ≥ 85% |

### 2.2 生成层指标

| 指标 | 定义 | 方法 |
|---|---|---|
| **答案正确性** | 关键数值/结论是否正确 | 关键词匹配 + 人工核对 |
| **忠实度（faithfulness）** | 答案中的每个论断是否都能在检索到的资料中找到依据 | 人工逐句核对 / LLM-as-judge |
| **引用覆盖率** | 有引用需求的题中，答案是否带上了引用 | 应为 100% |
| **人工评分** | 1~5 分（相关性、准确性、完整性、可读性） | ≥ 4.0 |

### 2.3 系统层指标

| 指标 | 目标 |
|---|---|
| 问答首字延迟 (TTFT) | < 3s |
| 完整回答耗时 | < 20s |
| 单份 PDF（40 页）解析耗时 | < 5min |
| 解析状态端到端可见延迟 | < 2s |

## 3. 对比实验（最有说服力的部分）

**同一套 30 道题，跑三种检索配置对比**：

| 配置 | 说明 |
|---|---|
| **A. 仅 BM25** | 关掉向量路，只有 `chunks.tokens` 的关键词检索 |
| **B. 仅向量** | 关掉 BM25，只有 chunk 向量 kNN |
| **C. 混合 RRF（本方案）** | BM25 + 向量 + 图片向量，三路 RRF |

**预期结论**（需要在实测后填入真实数字）

```
                 Hit@8    MRR     图片召回率
仅 BM25           0.xx    0.xx    0.xx
仅向量            0.xx    0.xx    0.xx
混合 RRF          0.xx    0.xx    0.xx
```

**要证明的三个论点**（每个论点都对应一组数据）

1. **混合优于单路** —— 纯向量漏掉专有名词/数字（BM25 补上），纯 BM25 漏掉改写表述（向量补上）。
2. **图片路有独立价值** —— 在 B 类（必须看图）题上，加了图片路后 Hit@8 明显提升；纯文字方案在这里必然接近 0。
3. **jieba 预分词 + BM25 不输 IK 插件** —— 用同一套索引做对照，或引用公开基准说明。

> 若图片路提升不明显，**如实记录并分析原因**（如 `openai` 后端下降级为 caption 文本召回 → 提升有限），这比伪造数据诚实得多，也是很好的"局限性分析"答辩素材。

## 4. 评测脚本设计

```python
# backend/tests/eval/evaluate.py
@dataclass
class EvalCase:
    id: str
    question: str
    category: str
    answer_docs: list[str]
    answer_pages: list[int]
    answer_images: list[str]
    keywords: list[str]


@dataclass
class EvalResult:
    case_id: str
    hit_at_8: bool
    reciprocal_rank: float
    image_recalled: bool
    cited_image_ids: list[str]
    citation_correct: bool
    answer: str
    keyword_coverage: float      # 标注关键词被覆盖的比例
    ttft_ms: int
    total_ms: int
```

**运行方式**

```bash
python -m tests.eval.evaluate \
  --cases docs/eval/cases.yaml \
  --config hybrid \
  --out docs/eval/results_hybrid.json
```

**输出**

```json
{
  "config": "hybrid",
  "total": 30,
  "hit_at_8": 0.87,
  "mrr": 0.74,
  "image_recall": 0.80,
  "citation_accuracy": 0.85,
  "keyword_coverage": 0.82,
  "avg_ttft_ms": 2100,
  "avg_total_ms": 11400,
  "by_category": {
    "A": {"hit_at_8": 0.90},
    "B": {"hit_at_8": 0.80},
    "C": {"hit_at_8": 0.80}
  }
}
```

## 6. 验收标准

**必须全部满足才算完成**

- [ ] 功能 1：能上传多份 PDF，全部进入 `done` 状态，ES 中可查到对应 chunks 与 images
- [ ] 功能 2：四个状态（pending/processing/done/failed）均可在前端观察到；失败有可读原因 + 可重试
- [ ] 功能 3.1：提问后返回**图文混排**答案（正文 + 至少一张引用图，图片可点开）
- [ ] 功能 3.2：带图提问能正常工作，答案结合了用户图
- [ ] 引用协议：至少 80% 的题目产出了 `[[cite:...]]` 标记并被正确渲染
- [ ] 混合检索 Hit@8 ≥ 85%
- [ ] 评测报告 `docs/评测报告.md` 完成，含三组对比数据 + 局限性分析

## 7. 演示脚本（答辩用，约 5 分钟）

```
1. 打开前端 → 上传 3 份 PDF（含一份图表密集的财报）
   → 现场展示：列表立刻出现"待解析"，随后实时变为"解析中（caption 55%）"、"解析完成"

2. 提问一个纯文本问题 → 展示图文混排答案 + 引用卡片
   → 点击引用图，弹出大图 + 来源页码

3. 提问一个必须看图的问题（截图给用户看）
   → 展示答案准确引用了图片中的数值

4. 上传一张截图作为"图问" → 展示图片被送入模型并参与回答

5. 展示 docs/评测报告.md 的对比表
   → 强调：仅文本方案在 B 类题上的失败，对比本方案

6. 展示 Kafka 的消费组滞后与状态事件流
   → 强调：Kafka 承担的是异步解析管道，不是聊天链路
```
