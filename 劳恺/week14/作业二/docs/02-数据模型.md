# 02 · 数据模型

## 1. 全局概览

系统里流转着四种数据结构：

```
① MinerU content_list  —— 外部系统的原始输出（解析产物）
        │  映射规则（见 §3）
        ▼
② 内部文档模型        —— 我们的统一表示（ChunkDoc / ImageDoc / DocumentDoc）
        │  向量化
        ▼
③ ES 文档             —— 落库形态（4 个索引）
        │
        ▼
④ 检索结果 / SSE 事件 —— 对外形态（RetrievedChunk / ChatDelta / ChatCitation）
```

## 2. Elasticsearch 索引设计

### 2.1 索引清单

| 索引 | 粒度 | 用途 | 主要查询 |
|---|---|---|---|
| `mmrag-documents` | 每个上传文件一条 | 元数据 + 解析状态 | 列表展示、状态查询、按 `doc_id` 删内容 |
| `mmrag-chunks` | 每个检索块一条 | 文本 + 块向量 + 绑定图片 | BM25 检索、kNN 检索 |
| `mmrag-images` | 每张图片一条 | caption + 图片向量 | 图片向量 kNN（第三路召回） |
| `mmrag-sessions` | 每个会话一条 | 聊天历史 | 按 `session_id` 取回 |

> **为什么图片要单独一个索引？** ES 的 `dense_vector` kNN 不支持在 `nested` 字段上高效检索。把图片提到独立索引后，第三路「图片向量召回」可以直接用 kNN，再通过 `chunk_id` 反查文字块，避免 nested 的性能坑与复杂度。

### 2.2 `mmrag-chunks` mapping

```json
{
  "settings": {
    "analysis": {
      "analyzer": {
        "jieba_tokens": {
          "type": "custom",
          "tokenizer": "whitespace",
          "filter": ["lowercase"]
        }
      }
    }
  },
  "mappings": {
    "properties": {
      "chunk_id":     { "type": "keyword" },
      "doc_id":       { "type": "keyword" },
      "doc_filename": { "type": "keyword" },
      "seq":          { "type": "integer" },
      "page_start":   { "type": "integer" },
      "page_end":     { "type": "integer" },

      "text":  { "type": "text", "analyzer": "standard",
                 "fields": { "raw": { "type": "keyword", "ignore_above": 512 } } },
      "tokens":{ "type": "text", "analyzer": "jieba_tokens" },

      "block_types": { "type": "keyword" },
      "bboxes":      { "type": "object", "enabled": false },

      "images": {
        "type": "nested",
        "properties": {
          "image_id": { "type": "keyword" },
          "doc_id":   { "type": "keyword" },
          "page_no":  { "type": "integer" },
          "idx":      { "type": "integer" },
          "path":     { "type": "keyword" },
          "url":      { "type": "keyword" },
          "caption":  { "type": "text" },
          "bbox":     { "type": "float", "index": false },
          "width":    { "type": "integer" },
          "height":   { "type": "integer" }
        }
      },

      "vector": {
        "type": "dense_vector",
        "dims": 1024,
        "index": true,
        "similarity": "cosine"
      },

      "created_at": { "type": "date" }
    }
  }
}
```

**关键设计说明**

| 字段 | 为什么这么设计 |
|---|---|
| `tokens`（jieba 预分词，空格连接） | **中文 BM25 的核心**。入库时用 jieba 切词后用空格连接，ES 用自定义的 `jieba_tokens` 分析器（**whitespace 分词器 + lowercase**）切分，词边界被完整保留。⚠️ **不能用内置 `standard` 分析器** —— ES 的 standard 按 UAX#29 把中文**逐字切分**（"第三季度" → 第/三/季/度），会把 jieba 的分词结果重新打散，jieba 预分词等于白做，BM25 路退化成单字匹配。这样**完全不需要 `analysis-ik` 插件**，规避了"插件版本必须与 ES 版本严格一致"的部署坑。`text` 字段保留原文（`standard`），供高亮与展示，不参与 BM25 检索。 |
| 索引级 `analysis.analyzer` | `jieba_tokens` 必须定义在**索引 settings** 里（不是集群级），这样索引可以自包含、不依赖集群配置。`lowercase` 保证英文大小写不敏感（`Qwen3` 与 `qwen3` 同词）。若将来改用 IK 插件，**必须同时去掉 jieba 预分词** —— 两套方案对同一字段互斥，叠加会导致二次切分。 |
| `images` 用 `nested` | 图片是 chunk 的**从属实体**，需要独立于 chunk 的其他数组字段做过滤。若用普通 object，多值数组会交叉展开导致过滤语义错误。 |
| `vector.index: true` | 开启 HNSW 索引，否则 kNN 退化为暴力扫描。1024 维 + cosine 是 ES 8.x 的推荐组合。 |
| `bboxes` 关闭索引 | 只用于回显"图在页面上的位置"，不参与检索，`enabled: false` 省空间。 |

### 2.3 `mmrag-images` mapping

```json
{
  "mappings": {
    "properties": {
      "image_id": { "type": "keyword" },
      "doc_id":   { "type": "keyword" },
      "doc_filename": { "type": "keyword" },
      "chunk_id": { "type": "keyword", "description": "绑定的文字块" },
      "page_no":  { "type": "integer" },
      "idx":      { "type": "integer" },
      "path":     { "type": "keyword" },
      "url":      { "type": "keyword" },
      "caption":  { "type": "text" },
      "tokens":   { "type": "text", "analyzer": "jieba_tokens" },
      "bbox":     { "type": "float", "index": false },
      "width":    { "type": "integer" },
      "height":   { "type": "integer" },
```

`caption` 与 `tokens` 都是 text：BM25 走 `tokens`（jieba 预分词），`caption` 用于高亮与人工核对。

### 2.5 `mmrag-sessions` mapping

```json
{
  "mappings": {
    "properties": {
      "session_id": { "type": "keyword" },
      "messages":  { "type": "object", "enabled": false },
      "created_at":{ "type": "date" },
      "updated_at":{ "type": "date" }
    }
  }
}
```

`messages` 关闭索引（整体读写，不做检索），内容形如：

```json
[
  {"role": "user", "content": "这张图里的营收峰值在哪个季度？",
   "images": [{"filename": "shot.png", "sha256": "…"}], "created_at": "…"},
  {"role": "assistant", "content": "根据《财报.pdf》第 7 页的柱状图【图1】，峰值出现在 2024Q3。",
   "citations": [{"image_id": "d_ab12_p7_i1", "url": "/static/images/d_ab12/p7_i1.png", "page_no": 7}],
   "created_at": "…"}
]
```

> **历史里的图片不重传**：历史消息只存图片的**引用信息**（文件名、哈希），不存 base64，也不重新送给模型。重发历史会显著增加 token 与显存开销，且多数场景无必要。

## 3. MinerU `content_list` → 内部模型映射

MinerU 输出的 `content_list.json` 是一个数组，每个元素代表一个版面块：

```json
[
  {"type": "text", "text": "## 1. 引言\n本文研究……", "text_format": "markdown",
   "page_idx": 0, "bbox": [72.0, 100.2, 523.8, 180.4]},

  {"type": "image", "img_path": "images/abc123.jpg", "image_caption": "图 1 营收趋势",
   "page_idx": 2, "bbox": [120.0, 300.0, 480.0, 520.0]},

  {"type": "table", "table_body": "<table><tr><td>季度</td><td>营收</td></tr>…</table>",
   "page_idx": 3, "bbox": [70.0, 200.0, 525.0, 400.0]},

  {"type": "equation", "text": "E = mc^2", "text_format": "latex", "page_idx": 4}
]
```

**页码换算**：`page_idx` 是 **0 基**，内部一律用 **1 基** `page_no = page_idx + 1`。

### 3.1 元素类型处理规则

> ⚠️ **以下类型表已按 2026-11-12 实测校准**（详见 `05-MinerU接入.md` §5.1）。
> 实测样本中**没有** `image` 与 `equation` 块，图片以 `table.img_path` 出现；
> 另外还有 `footer` / `page_number` 两类噪声块。实现保留了这些分支的容错。

| `type` | 提取内容 | 转换 | 是否独立成块 |
|---|---|---|---|
| `text` | `text` 字段 | 原样保留（**无 `text_format` 字段**） | 参与合并 |
| `table` | `table_body`（HTML） | **HTML → Markdown 表格**（`| a | b |` 形式）；解析失败则去标签取纯文本 | 参与合并（超长按 max_tokens 切分） |
| `equation` | `text` 字段 | 包成 `$...$` 保留 LaTeX | **独立成块**（不与正文混排，但**参与检索**）；短公式块**不参与碎块合并** |
| `image` | `img_path` + `image_caption` | 图片落地为文件，记录 `ImageRef` | **不独立成块**，绑定到相邻文字块 |
| `footer` / `page_number` | — | **跳过**（纯噪声，不入库） | 否 |
| 其他未知类型 | `text` / `content` | 降级当正文处理 | 参与合并 |

> `table_caption` / `table_footnote` 实测是 **`list`**，必须 join 后拼接，否则会得到 `[]` 字面量。

> **为什么表格要转 Markdown 而不是塞 HTML？** HTML 噪声大（`<span style=...>`、实体），既占 token 又干扰 BM25 分词。Markdown 表格既紧凑又是合法文本，双重收益。

> **为什么公式独立成块？** 公式与正文混排会破坏数学表达；独立成块后，用户问"这页的公式是什么"仍能精确命中。

### 3.2 文字块合并规则

```
遍历连续的 text 块（同页或跨页）：
  累积 token 数
  ├─ 超过 max_tokens(900)  → 切分当前块，剩余部分开新块
  ├─ 达到 target_tokens(600) → 可切点（优先在段落边界切）
  └─ 新块开头复用上一块尾部 overlap_tokens(100) 个 token
合并阶段：
  └─ 产出块 token 数 < min_tokens(30) → 并入相邻块（优先后一块，否则前一块）
```

- 切分点优先选**段落边界**（`\n\n`），避免把句子劈成两半。
- 重叠（overlap）保证跨块语义连续，避免"答案正好在切口上"。
- 碎块合并避免拉低召回质量（太短的块在 BM25 里噪声大）。

### 3.3 图片绑定规则

**图片不单独成块**，而是绑定到**相邻的文字块**：

```
对每张图片 P（在 content_list 的块序列中的位置 i）：
  1. 向前找最近的文字 chunk C1，要求同页或前一页
  2. 若无 C1，向后找最近的文字 chunk C2
  3. 若仍无 → 丢弃该图片（计入 stats，不入库）
  4. 绑定后：
       chunk.images  += ImageRef
       新建 ImageDoc{chunk_id: C.id}
```

**为什么这样绑定？**
- 图片本身没有可靠的文本表示（除 caption 外），单独成块会让向量空间变得稀疏且不稳定。
- 绑定后，"命中这段文字"自然就"命中了旁边的图"，这是图文混排输出的前提。
- 图片与文字同页 → 语义相关性强，模型能正确理解图与文的对应关系。

**落盘与 ID**

```
图片文件：/data/images/{doc_id}/{image_id}.png      （统一转 PNG）
image_id：{doc_id}_p{page_no}_i{idx}                （idx 为该页内序号，从 1 开始）
path：    {doc_id}/{image_id}.png                    （相对 image_dir）
url：     /static/images/{doc_id}/{image_id}.png      （对外可访问路径）
```

## 4. 内部文档模型（Pydantic）

```python
class ImageRef(BaseModel):
    image_id: str          # d_ab12_p7_i1
    doc_id: str
    page_no: int           # 1 基
    idx: int
    path: str              # d_ab12/d_ab12_p7_i1.png
    url: str               # /static/images/d_ab12/d_ab12_p7_i1.png
    caption: str = ""
    bbox: list[float] | None = None
    width: int | None = None
    height: int | None = None


class ChunkDoc(BaseModel):
    chunk_id: str          # d_ab12_c0007
    doc_id: str
    doc_filename: str
    seq: int               # 文档内序号，从 0 开始
    page_start: int
    page_end: int
    text: str              # 表格=md，公式=$...$
    tokens: str            # jieba 分词后空格连接
    block_types: list[str] # ["text","table"]
    bboxes: list[list[float]]
    images: list[ImageRef]
    vector: list[float]    # 1024 维
    created_at: datetime


class ImageDoc(BaseModel):
    image_id: str
    doc_id: str
    doc_filename: str
    chunk_id: str          # 反查所属块
    page_no: int
    idx: int
    path: str
    url: str
    caption: str = ""
    tokens: str = ""
    bbox: list[float] | None = None
    width: int | None = None
    height: int | None = None
    vector: list[float]    # 图片向量（统一空间）
    created_at: datetime


class DocumentDoc(BaseModel):
    doc_id: str
    filename: str
    file_path: str
    content_hash: str
    size_bytes: int
    page_count: int | None
    status: Literal["pending", "processing", "done", "failed"]
    progress: float        # 0.0 ~ 1.0
    stage: str             # queued/mineru_parse/chunking/caption/embedding/indexing
    error: str | None
    chunk_count: int
    image_count: int
    parser: str            # "mineru"
    parse_duration_ms: int | None
    created_at: datetime
    updated_at: datetime
    finished_at: datetime | None
```

## 5. 磁盘布局

```
/data/
├── uploads/
│   └── {doc_id}.pdf                 原始上传文件
├── images/
│   └── {doc_id}/
│       └── {image_id}.png           抽取的图片（转 PNG）
└── work/
    └── {task_id}/                   MinerU 产物的解压目录（可定期清理）
        ├── *.md
        ├── content_list.json
        └── images/…
```

**清理策略**：`work/` 是临时目录，解析成功后即可删除（图片已转存到 `images/`）；建议加一个定时任务清理 24 小时前的 `work/` 目录。
