# 06 · RAG 与多模态设计

> 本文是问答链路的技术核心：**怎么检索、怎么把图文喂给模型、怎么保证答案有据可查**。

---

## 1. 整体流程

```
用户问题 q（含可选用户图片）
        │
        ├─ embed(q) ────────────→ query_vector (1024d)
        │
        ├─ ① BM25 路    查 chunks.tokens  (jieba 预分词)
        ├─ ② 向量路    kNN over chunks.vector
        ├─ ③ 图片向量路 kNN over images.vector → chunk_id
        │
        ├─ RRF 融合 → top-8 chunks
        │
        ├─ 从这 8 个 chunk 中挑选**最多 4 个带图的**，收集其 ImageRef
        │
        ├─ 组装 Prompt（图文交替）
        │
        ├─ vLLM 流式生成
        │
        ├─ 边流边识别 [[cite:img_id]] → 发 citation 事件 + 正文替换为【图N】
        │
        └─ done 事件（完整答案 + citations + 命中的 chunk_id）
```

## 2. 嵌入模型

### 2.1 为什么用 Qwen3-VL-Embedding-0.6B

| 需求 | Qwen3-VL-Embedding-0.6B | bge-m3 | CLIP / SigLIP |
|---|---|---|---|
| 中文语义 | 强 | 强 | 弱（中英混排文档不适用） |
| **图文统一空间** | ✅ | ❌ 仅文本 | ❌ 仅图像 |
| 图片可直接向量化 | ✅ | ❌ | ✅ |
| 显存 | ~1.5GB | CPU 可跑 | ~1GB |
| 维度 | 1024 | 1024 | 512~768 |

> **Qwen3-VL 本身不能当嵌入模型用**：它是生成式模型（ViT + LLM），内部编码器没有暴露成通用检索 embedding API。同族的 **Qwen3-VL-Embedding / Qwen3-VL-Reranker** 才是配套的检索模型（论文 arXiv:2601.04720，支持文本/图片/视频统一空间）。

**统一空间的实际价值**：用户问"图里这个折线的拐点在第几季度"，纯文本检索无法命中（关键词不在文本里），但**图片向量与问题文本在同一空间**，可以召回。这正是"真多模态召回"与"检索到图再让模型看图"的本质差别。

### 2.2 三种后端与降级

| 后端 | 文本 | 图片 | 说明 |
|---|---|---|---|
| `local` | ✅ 本地模型 | ✅ **同模型同空间** | 需装 `transformers` + `sentence-transformers`，懒加载到 GPU/CPU |
| `openai` | ✅ `/v1/embeddings` | ⚠️ **降级**：用 caption 文本的向量顶替 | 语义等价性弱于真图片编码，但可跑通 |
| `mock` | 确定性伪向量 | 确定性伪向量 | 本地测试用（hash → 固定维度向量） |

**默认 `openai`（可用任何 OpenAI 兼容的文本 embedding 服务，如 bge-m3/TEI）+ 图片路走 caption 降级**；
若要让第三路召回真正有效，切到 `local` 用 Qwen3-VL-Embedding。

> **这影响"第三路召回"的价值**：`openai` 模式下第三路召回实际是"图片 caption 的文本召回"，与第一路 BM25 高度重叠，收益有限。**要拿到完整的多模态召回收益，必须用 `local` 后端。** 这点要在答辩时讲清楚，而不是含糊过去。

## 3. 混合检索与 RRF

### 3.1 三路的分工

| 路 | 查询对象 | 擅长 |
|---|---|---|
| ① BM25 | `chunks.tokens`（jieba 预分词） | 专有名词、数字、术语、罕见词（"2024Q3"、"GB/T 35273"） |
| ② 向量 | `chunks.vector` vs query_vector | 语义相近、改写、不同表述 |
| ③ 图片向量 | `images.vector` vs query_vector | 问题语义只体现在图里（图表数值、示意图结构） |

### 3.2 RRF 融合公式

```
score(d) = Σ_{r ∈ routes} 1 / (k + rank_r(d))     k = 60
```

- `rank_r(d)`：文档 d 在第 r 路结果中的排名（**从 1 开始**），未出现在该路则不计入。
- 各路先各取 **top-20**，融合后取 **top-8**。
- **为什么用 RRF 而不是加权求和？** BM25 分数与余弦相似度量纲完全不同，无法直接加权；RRF 只用**排名**，天然免疫量纲问题，且是 IR 界的标准做法（Cormack et al., 2009）。
- **k=60** 是原论文的经验值，作用是**压制头部**：rank1 与 rank2 的差距 = 1/61 − 1/62 ≈ 0.00026，rank20 与 rank21 的差距更小 → 避免"排第一的路完全主导结果"。

**手工验算示例**

| 文档 | BM25 排名 | 向量排名 | 图片排名 | RRF 分数 |
|---|---|---|---|---|
| A | 1 | 3 | — | 1/61 + 1/63 = **0.03226** |
| B | 2 | — | — | 1/62 = **0.01613** |
| C | — | 1 | 1 | 1/61 + 1/61 = **0.03279** |

→ 融合后顺序 **C > A > B**。C 只在两路出现（都是第一）因此胜出，A 在两路但排名靠后。

### 3.3 为什么不用 ES 内置 RRF

ES 8.14+ 的 `retriever` RRF 写法更简洁，但**版本要求高**（8.14+），且难以插入"图片路"这种自定义检索。自己在 Python 层实现 RRF：三路检索各自独立、可替换、可单测。

### 3.4 检索范围过滤

`doc_ids` 非空时，三路都加 `terms: {doc_id: [...]}` 过滤 → 前端"限定文档范围"功能。

## 4. 图片预算与选择

### 4.1 硬预算

| 来源 | 上限 | 理由 |
|---|---|---|
| 用户图片 | **4** | 用户主动提供的图，不能丢 |
| 文档图片 | **4** | 从 top-8 chunks 中挑选带图的块 |
| **合计** | **8** | 与 vLLM `--limit-mm-per-prompt '{"image":8}'` 对齐 |

### 4.2 文档图的选择策略

```
从 top-8 chunks（已按 RRF 分数排序）中：
  1. 筛出含图片的 chunks（保持 RRF 顺序）
  2. 取前 4 个，每个 chunk 取**第一张**图片
  3. 若某 chunk 有多张图且都是关键图（如多子图），最多再取 1 张
```

**为什么不把 8 个块的图全送？**
- 8 张图 × 每张 ~1280 visual token ≈ 10240 token，占 32K 上下文的 30%；
- 多图会**稀释模型对每张图的注意力**，关联准确率下降；
- 响应变慢。

### 4.3 图的预处理

发给 vLLM 前统一处理：

```
Pillow 打开 → 缩放到最长边 ≤1600px → 转 JPEG(quality=85) → base64
```

- 控制请求体大小（base64 比原始字节大约 33%）；
- 控制 visual token 数（与 `max_pixels=1003520` 配合）；
- PNG 转 JPEG 大幅减小图表类图片的体积。

## 5. Prompt 组装：图文交替

### 5.1 设计原则

> **图片必须紧贴它所属的文字块，不能集中放在末尾。**

在多模态 message 里，图与它的说明文字**相邻**时，模型对"哪张图对应哪段话"的判断准确率显著高于"图全在末尾 + 文本里用编号指代"。

### 5.2 消息结构示例

```jsonc
[
  { "role": "system", "content": "你是一个严谨的多模态 RAG 助手……（见 5.4）" },

  // 历史对话（最近 3 轮）
  { "role": "user",      "content": "上一轮的问题" },
  { "role": "assistant", "content": "上一轮的回答" },

  { "role": "user", "content": [
      // ① 用户图片排最前
      { "type": "image_url", "image_url": { "url": "data:image/jpeg;base64,…" } },
      { "type": "text", "text": "用户问题：2024 年营收峰值出现在哪个季度？\n\n" },

      // ② 文档图片：标记 + 图 + 紧邻的文字
      { "type": "text", "text": "<img id=\"d_ab12_p7_i1\" page=\"7\" caption=\"柱状图，横轴为季度，纵轴为营收（亿元）\">" },
      { "type": "image_url", "image_url": { "url": "data:image/jpeg;base64,…" } },
      { "type": "text", "text": "【来源：《2024年度财报.pdf》第 7 页】\n2024 年前三季度营收分别为 28.1 / 33.5 / 42.3 亿元……" },

      { "type": "text", "text": "<img id=\"d_ab12_p9_i2\" page=\"9\" caption=\"分季度营收同比增速折线图\">" },
      { "type": "image_url", "image_url": { "url": "data:image/jpeg;base64,…" } },
      { "type": "text", "text": "【来源：《2024年度财报.pdf》第 9 页】\n同比增速在 2024Q3 达到全年最高……" },

      // ③ 纯文字块
      { "type": "text", "text": "【来源：《产品手册.pdf》第 4 页】\n本产品支持…（该块无绑定图片）" }
  ]}
]
```

**关键点**
- `<img id=...>` 标记**紧贴**对应的图片，模型据此知道该图的 ID；
- 文字块带**来源标注**（书名 + 页码），让模型能生成带来源的答案；
- 用户图片在最前 → 前端渲染时 `【图1】`、`【图2】` 对应用户图，`【图3】` 起对应文档图。

### 5.3 图片序号与 `【图N】` 的对应

`【图N】` 的 N 是**本次送入模型的图片列表的 1 基序号**：

```
送模图片列表 = [用户图1, 用户图2, ..., 文档图A, 文档图B, ...]
→ 用户图1 = 图1, 文档图A = 图3, 文档图B = 图4
```

前端据此渲染：`【图3】` → 展示 `citations` 里 `text == "【图3】"` 的那张图。

### 5.4 System Prompt

```text
你是一个严谨的多模态文档问答助手。请严格依据【参考资料】回答用户问题。

要求：
1. 只使用参考资料中的信息，不要凭记忆补充未出现的内容。
2. 当你引用某张图片时，必须在对应句子后插入 [[cite:{image_id}]] 标记，
   image_id 原样抄写我提供的 id（例如 [[cite:d_ab12_p7_i1]]），不要改写或编造。
3. 文字块后的【来源：《文件名》第 N 页】已经标明出处，回答时请保留这个来源信息。
4. 如果参考资料不足以回答，明确说明"资料中没有相关信息"，并指出还需要哪些信息。
5. 不要编造页码、图号或数据。
6. 回答用简体中文，结构清晰；涉及图表数据时请结合图片内容描述趋势与关键数值。
```

**少样本示例（放进 system prompt，能显著提高标记格式命中率）**

```text
示例：
用户问：营收峰值在哪个季度？
回答：营收峰值出现在 2024 年第三季度【来源：《2024年度财报.pdf》第 7 页】[[cite:d_ab12_p7_i1]]，
      对应营收为 42.3 亿元。
```

## 6. 引用协议

### 6.1 标记语法

```
[[cite:<image_id>]]
```

`image_id` 形如 `d_ab12cd34ef56_p7_i1`（字符集 `[A-Za-z0-9_\-:.]`）。

### 6.2 流式识别（关键实现细节）

模型是**逐 token** 吐字的，标记可能跨 chunk 断裂：

```
delta1: "…出现在 2024 年第三季度[[ci"
delta2: "te:d_ab12_p7_i1]]，对应营收…"
```

若直接转发，前端会看到半截标记。**处理办法**：维护一个缓冲区，**扣住可能是标记前缀的尾部**：

```python
HOLD = "[[cite:"            # 标记最长前缀
def process(buffer: str, pending: str) -> tuple[str, str]:
    """
    返回 (可安全输出的文本, 新的 pending)
    """
    # 找到 pending 中最后一个 "[" 的位置
    i = pending.rfind("[")
    if i >= 0 and "]]" not in pending[i:]:
        safe, pending = pending[:i], pending[i:]   # 扣住疑似标记
    else:
        safe, pending = pending, ""
    ...
```

当完整标记出现时：
1. 输出 `【图N】`（N = 该 image_id 在送模图片列表中的序号）；
2. 发一条 `citation` SSE 事件；
3. 标记已知的 image_id 进 `cited_image_ids`（去重、保序）。

### 6.3 降级

| 情况 | 行为 |
|---|---|
| 标记里的 image_id 不在本次送模列表 | **原样保留** `[[cite:xxx]]` 文本（可读降级），不产生 citation 事件 |
| 整条回答没有任何标记 | 正常输出；`done.citations` 退化为"本次检索到的全部图片" |
| 模型输出了乱格式（如 `[图1]`） | 当普通文本输出，不报错 |

> 降级原则：**宁可多显示一点原始文本，也不丢内容、不报错**。

## 7. 会话历史

| 项 | 决策 |
|---|---|
| 存储 | ES `mmrag-sessions` |
| 携带轮数 | 最近 **3 轮**（`chat_history_turns`） |
| 历史图片 | **不重传**。历史消息只存图片的文件名与哈希 |
| 历史引用 | 存 `citations` 元数据，前端重渲染历史消息时直接用 |

**为什么只带 3 轮？** 上下文预算：8 张图 ≈ 10K token，文档正文 ≈ 3K token，3 轮历史 ≈ 2K token，答案 ≈ 2K token → 总计约 17K，在 32K 窗口内安全。


**调参指引**

| 想改善 | 调什么 | 注意 |
|---|---|---|
| 召回不全 | `TOP_K_FINAL` ↑、`TOP_K_BM25/vector` ↑ | 会增加 token 与延迟 |
| 答案跑题 | `TOP_K_FINAL` ↓、`LLM_TEMPERATURE` ↓ | 资料少时更聚焦，但也可能漏 |
| 引用格式不稳定 | system prompt 加 few-shot、`LLM_TEMPERATURE` ↓ | 必要时后处理纠错 |
| 切片太碎/太整 | `CHUNK_TARGET_TOKENS` | 中文 600 token ≈ 400~500 字 |
| 图片召回差 | 切到 `local` 嵌入后端 | 见 §2.2 |
