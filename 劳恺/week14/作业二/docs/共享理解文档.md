# 共享理解文档 —— Kafka 多模态 RAG 问答系统

> 本文档是需求澄清（grilling）的最终共识。所有实现以本文档为准。
> 版本：v1.0 ｜ 定案日期：2026-11-11

---

## 1. 项目目标

基于 Kafka 构建一个**多模态 RAG 问答系统**：

- **功能 1**：前端可批量上传 PDF → 经 Kafka 投递到后端 → 后端用 MinerU 解析 → 切块、向量化、入库。
- **功能 2**：前端可见每个文档的解析状态：`pending`（待解析）/ `processing`（解析中）/ `done`（解析完成）/ `failed`（解析失败）。
- **功能 3**：多模态问答
  - 3.1 文字提问 → **图文混排**输出（正文 + 从 PDF 抽取的原图 + 来源标注）。
  - 3.2 图问：用户提问可带图片（截图/照片），与检索到的文档证据一起送 LLM 回答。

**交付顺序**：后端先行，前端最后（前端契约本文档已锁定）。

## 2. 总体架构

```
                     ┌──────────── 云端服务器（单机） ────────────┐
 浏览器 ──HTTP/SSE──▶ │  后端 FastAPI (8080)                       │
                     │    ├─ REST: 上传/列表/删除/重试/静态图      │
                     │    └─ SSE : 状态流 / 问答流                 │
                     │            │                               │
                     │            ├─ produce ──▶ Kafka (9092)     │
                     │            │              pdf.upload       │
                     │            │              pdf.parse.status │
                     │            │              pdf.upload.dlq   │
                     │            │                  ▲           │
                     │            │                  │ consume   │
                     │            │            解析 Worker         │
                     │            │              ├ MinerU 官方 API │
                     │            │              ├ 切块 / caption  │
                     │            │              ├ Embedding      │
                     │            │              └ 写 ES          │
                     │            ▼                               │
                     │        Elasticsearch (9200)                 │
                     │          mmrag-documents / chunks / images  │
                     │            ▲                               │
                     │            └─ 向量检索 ──┐                 │
                     │  vLLM (8000) ◀───────────┘                │
                     │    Qwen3-VL-8B-Instruct  (生成)            │
                     │    Qwen3-VL-Embedding-0.6B (图文统一空间)   │
                     └────────────────────────────────────────────┘
```

**关键原则**：Kafka 只承载「慢任务」（上传→解析→索引）链路；问答走 HTTP + SSE 直连，保证交互延迟。
状态真相在 Elasticsearch，任何读法（轮询 / SSE）结果一致。

## 3. 决策清单（定案）

### 3.1 部署与基础设施

| 项 | 决策 | 理由 |
|---|---|---|
| 拓扑 | **全部部署在云端服务器** | 本地关机会导致 Kafka 消费者停摆、状态卡死；避免图片反复走公网；前后端一套环境 |
| 显存 | **48GB** | Qwen3-VL-8B(bf16 ~17GB) + Embedding-0.6B(~1.5GB) + 预留 25GB+ 给 KV cache / 长上下文 / 未来 reranker |
| Kafka | 单节点 **KRaft** 模式（无 ZooKeeper） | 单用户小规模；1 broker 足够 |
| 端口隔离 | Kafka(9092) / ES(9200) / PG **仅监听 127.0.0.1**；对外仅开 vLLM(8000)、后端(8080)、前端(80) | 缩小攻击面 |
| 编排 | docker compose | 一条命令起全套 |

### 3.2 模型与解析

| 项 | 决策 |
|---|---|
| 生成模型 | **Qwen3-VL-8B-Instruct**，vLLM 部署，OpenAI 兼容 `/v1/chat/completions` |
| vLLM 参数 | `--max-model-len 32768~65536`、`--limit-mm-per-prompt '{"image":8,"video":0}'`、`--mm-processor-kwargs '{"max_pixels":1003520}'`、`--gpu-memory-utilization 0.80` |
| 图片传输 | **base64 data URL**（不走公网 URL，避免超时/防盗链/热链失效） |
| 嵌入模型 | **Qwen3-VL-Embedding-0.6B**，图文统一向量空间，1024 维 |
| PDF 解析 | **MinerU 官方精准解析 API v4**（`POST /api/v4/extract/task`）。不自建，不与 vLLM 抢显存 |
| MinerU 适配 | `MineruClient` 适配器，**endpoint / 鉴权 / 提交模式（url / upload）全部可配置**，两种模式都实现，接入时只改 `.env` |
| MinerU 提交模式 | 默认 **upload**（两段式：申请签名链接 → PUT 到 OSS）；备选 **url**。官方**不支持 multipart / base64 直传** |
| Agent 轻量 API | ❌ **不可用**：只输出 Markdown，无 zip / content_list / 图片，且限 10MB / 20 页 |

> Qwen3-VL 是生成式模型，其内部 ViT 不可直接当检索 embedding 用；因此使用同族的 **Qwen3-VL-Embedding** 做向量化。

### 3.3 存储与检索

| 项 | 决策 |
|---|---|
| 存储 | **Elasticsearch 8**（三个索引：`documents` / `chunks` / `images`） |
| 中文检索 | 入库时 **jieba 预分词**写入 `tokens` 字段（避开 analysis-ik 插件的版本地狱），BM25 走该字段 |
| 向量 | `dense_vector` 1024 维，cosine，`index: true` (HNSW) |
| 融合 | ES 内置 **RRF**，BM25 与 kNN 两路融合 |
| 切块 | MinerU 版面块为原子 → 按 token 合并成 chunk（目标 600 token，重叠 100，最小 30） |
| 特殊块 | 表格 → Markdown 表格文本；公式 → LaTeX；图片 → **不单独成块，绑定到相邻文字块** |
| 图片 caption | 用 Qwen3-VL 为每张图生成 1~2 句描述存库 → **图片内容可被 BM25 关键词命中** |
| 最终召回 | RRF 融合 **top-8** 块（不 rerank），其中**最多 4 个带图的块**送图 |
| 检索范围 | 默认全库，前端提供文档多选器 |

### 3.4 消息与状态

| 项 | 决策 |
|---|---|
| Topic | `pdf.upload`（任务）、`pdf.parse.status`（状态事件）、`pdf.upload.dlq`（死信） |
| 语义 | 至少一次 + **消费者幂等**（`doc_id` + `chunk_id` 幂等键，重放不产生重复块） |
| offset | **先写 ES、成功后再提交 offset**（崩溃重放靠幂等兜底） |
| 分区 | `pdf.upload` 分区数 = worker 并发数，key = `doc_id`（同一文档串行） |
| 重试 | 消息头带 `attempt`，超阈值进 DLQ；文档状态置 `failed` + 可读错误 + 前端「重试」按钮 |
| 状态机 | `pending → processing → done` / `failed`；**任何失败都必须落到明确的 failed，绝不永久卡在 processing** |
| 超时兜底 | 单文档解析超时（默认 30 分钟）判失败 |

### 3.5 问答与协议

| 项 | 决策 |
|---|---|
| 问答入口 | `POST /api/chat`（SSE），**不走 Kafka**（交互式低延迟场景） |
| 事件类型 | `delta`（增量文本）/ `citation`（引用某张图）/ `done`（结束，带 citations 数组）/ `error` |
| 引用协议 | prompt 中给每张图注入 `<img id="...">` 标记，要求 LLM 输出 `[[cite:<id>]]`；后端正则解析 → 发 `citation` 事件 → 正文保留可读降级 |
| 图文排布 | **text→image→text→image 交替**，图片紧贴所属块文字（关联准确率显著高于图片集中末尾） |
| 图片预算 | 用户图 ≤4（base64 直传，不落盘）+ 文档图 ≤4（文件系统存储，走 `/static/images/...`）= 总计 ≤8 |
| 会话历史 | 持久化到 ES；携带最近 3 轮；历史图片不重传 |
| 流式 | vLLM `stream=true`，逐 token 推 `delta` |

### 3.6 工程

| 项 | 决策 |
|---|---|
| 后端 | Python 3.12 + FastAPI + Pydantic v2 + httpx / openai-sdk |
| 目录 | `backend/` `frontend/` `deploy/` `docs/`（monorepo） |
| 部署 | docker compose：kafka(KRaft) + elasticsearch + backend(api) + backend(worker) + vllm |
| 可测试性 | **Mock 模式**：MinerU / LLM / Embedding 均有 mock 实现，无云端服务器也能端到端跑通全链路 |

## 4. API 契约（前后端边界）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/documents` | multipart 批量上传 PDF → 202 + `[{doc_id, status:"pending"}]` |
| GET | `/api/documents` | 文档列表（状态、页数、块数、图片数、缩略图） |
| GET | `/api/documents/{doc_id}` | 单文档详情 |
| DELETE | `/api/documents/{doc_id}` | 删除文档及其块/图 |
| POST | `/api/documents/{doc_id}/retry` | 重试解析（重发 `pdf.upload`） |
| GET | `/api/documents/events` | **SSE** 状态流：`{"event":"status","doc_id":..,"status":..,"progress":..,"stage":..}` |
| GET | `/static/images/{doc_id}/{filename}` | 图片静态访问（后端做路径穿越校验） |
| POST | `/api/chat` | **SSE** 问答：`{session_id?, question, images[]?, doc_ids?}` |
| GET | `/api/sessions/{session_id}` | 会话历史 |
| GET | `/healthz` | 健康检查 |

## 5. 风险与遗留

> MinerU 官方接口已于 2026-11-11 实际抓取核验，结论见 [05-MinerU接入.md](05-MinerU接入.md)。

1. **`content_list.json` 字段级定义官方未公开** → 官方 API 文档只链接到 output_files 页，而该页已改为 MinerU 4.1 的 `docvortex` 新协议（`pages[].blocks[]`），与经典字段表不是同一套。
   → **实施第一步必须实测**：跑一次任务后打印 `set(k for e in content_list for k in e)` 与 `type` 分布，据此定稿切块代码；解析代码写成字段容错的。
2. **免费额度 1000 页/天（高优先级）** → 50 份 × 40 页 ≈ 2000 页会超限，超出部分降优先级排队（非硬停）。应对：用 `page_ranges` 按需截取、分批导入、前端提示额度。
3. **单文件限制** → ≤ 200MB、≤ 200 页。超页用 `page_ranges` 截断或拆分。
4. **提交频控** → 三个提交入口共用 50 文件/分钟；查询 1000 次/分钟。
5. **`no_cache` 必须为 true** → 默认有 15 分钟 URL 缓存，否则重解析会拿到旧结果。
6. **ES 单节点** → 仅适合演示规模；生产需 3 节点。
7. **显存竞争** → MinerU 走官方 API 已规避；将来若本地化 MinerU（vlm 后端），需与 vLLM 分卡。
8. **图片路召回的真实性** → 默认 `openai` 嵌入后端下，图片向量实为 caption 文本向量（降级），第三路召回收益有限。要拿完整收益需切到 `local` 后端的 Qwen3-VL-Embedding（图文真正统一空间）。这一点必须在评测报告中如实说明。

## 6. 验收口径

- **功能**：上传→状态流转→提问→图文混排答案，全链路可跑通。
- **量化**：自建 20~30 道评测题（10 纯文本 + 10 必须看图才能答 + 5 图表/表格题），统计 ① 检索命中率（正确 chunk 是否进 top-8）② 引用正确率 ③ 人工评分 1~5。
- **产物**：`docs/评测报告.md`。
