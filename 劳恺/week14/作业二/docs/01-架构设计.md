# 01 · 架构设计

## 1. 设计目标与约束

| 约束 | 来源 | 对架构的影响 |
|---|---|---|
| 单用户、< 50 份 PDF | 规模决策 | 不需要分布式、不需要多租户隔离；Kafka 单节点足够 |
| 必须在 Kafka 上体现"消息驱动" | 作业要求 | Kafka 承担**慢任务管道**（上传→解析→索引） |
| 问答要快（首字 < 10s） | 交互体验 | 问答**不走 Kafka**，走 HTTP + SSE 直连 |
| Qwen3-VL + MinerU 共处一机 | 部署决策 | MinerU 用**官方 API**（不占本机 GPU），vLLM 独占显存 |
| 前端最后做 | 交付顺序 | 契约先行，API 文档锁定后再写 Vue |

**核心设计原则：把 Kafka 用在最能体现其价值的地方（慢任务、可重试、可观测的异步管道），而不是为了用而用。**

### 2.2 逻辑组件与职责

| 组件 | 进程 | 职责 | 不负责 |
|---|---|---|---|
| `api` | FastAPI | 上传受理、文档 CRUD、状态 SSE、问答 SSE、会话 | 不做解析、不做向量化 |
| `worker` | Python 轮询进程 | 消费 `pdf.upload`、跑解析流水线、更新状态 | 不直接对外提供接口 |
| `status-bus` | API 进程内后台任务 | 消费 `pdf.parse.status`，扇出给 SSE 订阅者 | 不落库（状态真相在 ES） |
| `mineru-client` | Worker 内 | 调用 MinerU 官方 API，下载并解压产物 | 不做切块 |
| `chunker` | Worker 内 | `content_list` → chunk + 绑图 | 不做 embedding |
| `captioner` | Worker 内 | 用 Qwen3-VL 给图片写描述 | — |
| `embedder` | Worker 内 | 文本/图片 → 向量 | — |
| `es-client` | API + Worker | 索引读写、混合检索 | — |
| `llm-client` | API + Worker | vLLM 调用（流式/非流式/图片描述） | — |

> **为什么 API 与 Worker 分进程？** 解析是分钟级慢任务，与问答的毫秒级延迟要求冲突。分开后问答永远不会被解析任务堵住；且二者可独立扩缩容。

## 3. 三条主链路时序

### 3.1 入库链路（Kafka 驱动）

```
前端            API              ES           Kafka          Worker        MinerU      vLLM
 │  POST /documents (multipart)  │            │              │             │           │
 │──────────────────────────────▶│            │              │             │           │
 │                               │──落盘 PDF──▶│              │             │           │
 │                               │──建文档(pending)─▶│          │             │           │
 │                               │──produce pdf.upload──▶│      │             │           │
 │◀─── 202 {doc_id, status:pending} ───────────│              │             │           │
 │                               │              │              │             │           │
 │                          【状态变化从 Kafka 回流】◀─────────┼─────────────┤           │
 │◀── SSE status:processing (stage=mineru_parse, 0.05) ──────│             │           │
 │                               │              │              │──解析 PDF──▶│           │
 │                               │              │              │◀─content_list+zip──────│
 │                               │              │              │──切块/绑图──▶│           │
 │                               │              │              │──图片 caption ────────▶│
 │                               │              │              │◀──caption 文本─────────│
 │                               │              │              │──文本+图片向量───▶│     │
 │                               │              │              │◀──向量──────────────────│
 │                               │              │◀─bulk 写 chunks/images───────│       │
 │                               │              │              │              │           │
 │◀── SSE status:done (chunk_count, image_count) ──────────────│             │           │
```

**关键点**
- 上传接口**立即返回**（202），不等待解析 → 前端秒级反馈。
- 解析全过程的状态都经 `pdf.parse.status` 事件回流 → 前端看到实时进度。
- Worker 在**写 ES 成功之后**才提交 Kafka offset → 崩溃时消息重放，靠幂等键保证不产生重复块。

### 3.2 状态链路

```
Worker ──produce pdf.parse.status──▶ Kafka ──consume──▶ API 的 status-bus
                                                            │
                                          ┌─────────────────┼─────────────────┐
                                          ▼                 ▼                 ▼
                                      SSE 订阅者A        SSE 订阅者B        SSE 订阅者C
```

- 状态**真相在 ES**（`documents.status`）。Kafka 里的事件只是**变更通知**。
- 前端若错过事件（例如断网重连），`GET /api/documents` 能拉回全量真相 → **SSE 是加速器，不是唯一数据源**。
- 这是「至少一次 + 幂等」设计的直接收益：事件可能重复、可能乱序，但状态最终一致。

### 3.3 问答链路（不走 Kafka）

```
前端                  API                ES            vLLM
 │ POST /api/chat (SSE) │                  │              │
 │────────────────────▶│                  │              │
 │                     │─ embed(query) ───┼──────────────▶│
 │                     │◀─ query_vector ──┼──────────────│
 │                     │─ RRF: BM25 + kNN + 图片向量 ─────▶│  (三次检索)
 │                     │◀─ top-8 chunks(含图片引用) ───────┤
 │                     │─ 组装图文交替 Prompt              │
 │                     │──────── chat_stream(stream=true) ─▶│
 │◀─ SSE delta ──────────────────────────│◀─ token 增量 ─│
 │◀─ SSE citation ────────────────────────│  (命中 [[cite:...]])
 │◀─ SSE done (答案全文 + citations[]) ───│◀─ 流结束 ─────│
```

**关键点**
- 用户图片（base64）**排在最前**，检索到的文档图片**紧贴其所属 chunk 文字**。
- `citation` 事件在**流式过程中**就能发出（边生成边识别 `[[cite:...]]`），不必等全文结束。
- 检索是**三路**：BM25 + 块文本向量 + 图片向量，RRF 融合。

## 4. 失败处理与降级

| 失败点 | 检测 | 处理 | 用户可见 |
|---|---|---|---|
| PDF 损坏 / 加密 | MinerU 返回失败 | 重试 ≤N 次 → 状态 `failed` + 错误原文 | 前端红色徽章 + 重试按钮 |
| MinerU 超时 | 客户端超时（默认 30min） | 同上 | 同上 |
| MinerU 免费额度耗尽 | HTTP 429 / 特定错误码 | **降级**：本地 pipeline 后端（若已安装） | 提示"当前使用降级解析" |
| vLLM OOM | 客户端错误 | 退避重试 2 次 → 减小图片数重试 1 次 | SSE `error` 事件 |
| vLLM 超时 | 客户端超时 | 同上 | SSE `error` 事件 |
| Embedding 服务不可用 | 健康检查 | 该文档 `failed`（不污染已完成文档） | 状态徽章 |
| ES 写入失败 | 异常 | **不提交 offset**，消息重放 | 状态停留在 `processing`，日志告警 |
| Kafka 不可用 | 发送异常 | 上传接口返回 503 | 前端提示"服务繁忙" |
| 引用标记解析失败 | 正则未匹配 | **降级**：正文原样保留标记，citations 退化为"本次检索到的图" | 答案仍可读 |

**核心原则**：任何失败都必须落到一个**明确的终态**（`failed` + 可读原因），绝不允许文档永远停在 `processing`。

## 5. 幂等性与一致性

| 对象 | 幂等键 | 机制 |
|---|---|---|
| 文档 | `doc_id` | ES `index` 操作（固定 `_id`），重复写覆盖 |
| 检索块 | `{doc_id}_c{seq:04d}` | `seq` 由内容顺序决定 → 同内容同 ID；重解析前先按 `doc_id` 删除旧块 |
| 图片 | `{doc_id}_p{page}_i{idx}` | 同上；重解析前先删除 |
| 状态事件 | `doc_id + updated_at` | 事件可重复；ES 侧以最后一次写入为准 |

**为什么 chunk_id 用序号而不是 hash？** 因为重放同一份 PDF 时，块划分完全一致，序号必然一致。若用内容 hash，一旦切块参数调整就会产生全新 ID，旧块残留 → 需要额外清理逻辑。序号 + "重解析前先删" 组合更简单可靠。

## 6. 扩展性预留（当前不做，但接口已留）

| 未来需求 | 当前设计如何承接 |
|---|---|
| 多用户 | `documents` 与 `chunks` 加 `user_id` 字段即可；当前单用户无鉴权 |
| 真正的分布式 Kafka | topic 分区数已参数化；消费者用 `doc_id` 做 key 保证同文档串行 |
| 引入 reranker | 检索层预留 hook：RRF 融合后加一层 cross-encoder 重排 |
| 本地化 MinerU | `MineruClient` 是接口化的，`--backend vlm` 与 `--backend pipeline` 可切换 |
| 图片向量换模型 | `EmbeddingClient` 三种后端可切换，接口不变 |
