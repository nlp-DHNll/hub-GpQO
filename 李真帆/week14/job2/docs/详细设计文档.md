## 1. 项目概述

构建一个多模态 RAG 问答系统，包含两大功能：

| 功能 | 说明 |
|---|---|
| 知识库管理 | 前端多选上传 PDF → Kafka 投递 → 后端 MineRU 解析 → 切片 + 向量化入库；列表实时显示 **待解析 / 解析中 / 解析完成 / 解析失败** |
| 多模态问答 | 用户提问可带图片；先相似度检索 top3 判断相关性：相关则结合知识库回答（**回答支持图文混排**，可引用文档中图片），不相关则大模型自由回答；会话历史存 SQLite |

### 1.1 已确认的技术决策

| 决策点 | 结论 |
|---|---|
| MineRU | 本地 `mineru-kit` CLI（已验证可执行：`mineru-kit parse xx.pdf --format zip -o output.zip --tier advanced`） |
| LLM | DeepSeek API（key 留空待填）；文本回答 `deepseek-chat`，带图提问走视觉模型 `deepseek-flash`（用户 key 支持） |
| Embedding | 用户 vLLM 环境自部署（推荐 `BAAI/bge-m3`，OpenAI 兼容 `/v1/embeddings`）；代码做 provider 抽象，可一键切本地 fastembed 兜底 |
| 前端框架 | Vue 3（Composition API + `<script setup>`） | 按用户要求由 React 改为 Vue |
| 解析状态刷新 | SSE 实时推送（后端状态变化主动推前端） |
| 知识库列表 | 分页加载（每页 10 条 + 状态筛选） |
| 基础设施 | Kafka / Redis 由使用方自备（附 docker-compose.yml 参考），Python 环境自备 |

```
│  API 层: /api/documents  /api/sessions  /api/chat(SSE)  /api/events(SSE)                      │
│  Chat 服务: 图片理解(vision) → 检索 → 相关性判断 → RAG回答(SSE流式)                              │
│  SSE 网关: 订阅 Redis pub/sub → 推送给浏览器                                                    │
│  Producer: 上传落库(pending) → 发 Kafka                                                          │
└──────┬──────────────────────────▲─────────────────────────┬───────────────────────────────────┘
       │ produce                  │ Redis pub/sub          │ 读/写
       ▼                          │ (状态事件)              ▼
┌──────────────┐          ┌───────┴────────┐        ┌──────────────┐      ┌──────────────────┐
│   Kafka      │          │     Redis      │        │ SQLite       │      │ 文件存储          │
│ topic:       │          │ - 任务幂等锁    │        │ data/rag.db  │      │ data/uploads/    │
│ rag.doc.parse│          │ - 事件pub/sub  │        │ documents    │      │ data/parsed/{id}/│
└──────┬───────┘          └────────────────┘        │ chunks       │      │ data/chat_images/│
       │ consume                                    │ chat_sessions│      └──────── ▲─────────┘
       ▼                                            │ chat_messages│               │
┌────────────────────────── Worker 进程 (python -m app.worker.consumer) ──────────┴──────────┐
│  消费任务 → 置parsing → mineru-kit 解析 → 解压 → md切片 → embedding批量入库 → 置completed    │
│  (每一步状态变更: 写 SQLite + PUBLISH Redis)                                                  │
└─────────────────────────────────────────────────────────────────────────────────────────────┘
                    外部依赖: DeepSeek API (chat / vision / embedding)
```

**进程模型（共 2 个后端进程）**：

1. `uvicorn app.main:app` —— API + SSE + Kafka Producer
2. `python -m app.worker.consumer` —— 解析 Worker（消费 Kafka，调 mineru-kit）

两进程通过 SQLite(WAL 模式) 共享数据、通过 Redis pub/sub 传递状态事件。

**图片服务**：MineRU 提取出的文档图片、聊天图片均落盘 `data/` 目录，由 FastAPI `StaticFiles` 挂载对外提供 URL（`/static/...`），供前端与 LLM 上下文引用。

## 5. 基础设施设计

### 5.1 Kafka

- **Topic**：`rag.doc.parse`（partition 数 1 起步；key = `doc_id` 保证同文档任务有序）
- **消息格式**（value, JSON）：

```json
{ "doc_id": "d7f3...", "file_path": "data/uploads/d7f3....pdf", "file_name": "报告.pdf", "sent_at": "2026-11-12T10:00:00" }
```

- **Producer**（API 进程）：上传接口先落库（`pending`），再同步发送 Kafka；发送失败则状态置 `failed(error_msg=投递队列失败)`，前端可点重试。
- **Consumer**（Worker 进程）：group `rag-mineru-worker`。
  - **幂等**：处理前 `SET doc:lock:{doc_id} nx ex 3600`；拿不到锁说明任务在处理中，直接 ack 跳过（防重复消费 / 重试按钮与在途任务并发）。
  - **提交策略**：处理完成（含失败）后手动提交 offset —— 失败任务不无限重投，避免毒丸阻塞队列；恢复手段是界面上的"重新解析"按钮（重新 produce 一条）。
  - **超时**：`mineru-kit` 子进程超时默认 600s，可配。

### 5.2 Redis

| 用途 | Key / 频道 | 说明 |
|---|---|---|
| 解析任务幂等锁 | `doc:lock:{doc_id}` | SETNX + TTL 1h，处理完释放 |
| 状态事件总线 | `rag:events` (pub/sub) | Worker 每次状态变更 PUBLISH；API 进程订阅后转发到所有 SSE 连接 |

> Worker 与 API 是两个进程，SSE 连接挂在 API 进程上，所以状态事件必须经 Redis pub/sub 跨进程传递。Redis 不可用时降级：SSE 不可用，前端提供手动刷新按钮兜底，解析流程本身不受影响（状态最终都在 SQLite）。

### 5.3 SQLite（data/rag.db）

- 单库 `rag.db` 同时承载知识库与聊天历史（用户需求：知识库用 rag.db、会话历史用 SQLite，统一一个文件最简）。
- 开启 **WAL 模式**：两进程并发读写安全；写操作短事务。
- 服务启动时自动执行建表 DDL（幂等，`CREATE TABLE IF NOT EXISTS`）。

## 6. 数据库设计

```sql
-- 文档表
CREATE TABLE IF NOT EXISTS documents (
  id          TEXT PRIMARY KEY,            -- uuid4 hex
  file_name   TEXT NOT NULL,               -- 原始文件名
  file_size   INTEGER NOT NULL,            -- 字节
  file_path   TEXT NOT NULL,               -- data/uploads/{id}.pdf
  description TEXT DEFAULT '',             -- 简单描述(见 6.1)
  status      TEXT NOT NULL DEFAULT 'pending',  -- pending|parsing|completed|failed
  error_msg   TEXT DEFAULT '',             -- 失败原因
  page_count  INTEGER DEFAULT 0,           -- 页数(解析后回填)
  chunk_count INTEGER DEFAULT 0,           -- 切片数(解析后回填)
  updated_at  TEXT NOT NULL,               -- ISO时间, SSE乱序去重依据
  created_at  TEXT NOT NULL
);

-- 切片表(含向量)
CREATE TABLE IF NOT EXISTS chunks (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  doc_id      TEXT NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
  chunk_index INTEGER NOT NULL,            -- 文档内序号
  chunk_type  TEXT NOT NULL,               -- text|table|image
  heading     TEXT DEFAULT '',             -- 所属章节路径(如 "第2章 > 2.1 原理")
  content     TEXT NOT NULL,               -- markdown内容; image块为 ![](/static/...) 语法
  image_path  TEXT DEFAULT '',             -- chunk_type=image 时图片相对路径
  embed_text  TEXT NOT NULL,               -- 用于向量化的文本(image块=周边上下文文本)
  embedding   BLOB,                        -- float32序列化, 维度=模型dim
  created_at  TEXT NOT NULL,
  UNIQUE(doc_id, chunk_index)
);

-- 会话表
CREATE TABLE IF NOT EXISTS chat_sessions (
  id         TEXT PRIMARY KEY,
  title      TEXT NOT NULL DEFAULT '新会话', -- 自动取首条提问前20字
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

-- 消息表
CREATE TABLE IF NOT EXISTS chat_messages (
  id            TEXT PRIMARY KEY,
  session_id    TEXT NOT NULL REFERENCES chat_sessions(id) ON DELETE CASCADE,
  role          TEXT NOT NULL,             -- user|assistant
  content       TEXT NOT NULL,             -- 文本 / 回答markdown(可含图片)
  image_path    TEXT DEFAULT '',           -- user消息附图路径(空=无图)
  meta          TEXT DEFAULT '',           -- JSON: {related, top3:[{doc,chunk,score}], model}
  created_at    TEXT NOT NULL
);
```

### 6.1 文档"简单描述"生成策略

- 上传时：`description` = 文件名（去扩展名），状态 `pending`。
- 解析完成后：自动截取正文前 200 字（去 md 语法标记）回填，同时回填页数/切片数。
- 前端表格"描述"列直接展示该字段，满足"把文档简单描述存储一下"。

## 7. 后端设计

### 7.1 文档解析流水线（worker/pipeline.py）

```
consume(msg)
 ├─ 1. Redis SETNX 幂等锁; 拿不到 → ack跳过
 ├─ 2. status=parsing        → UPDATE + PUBLISH
 ├─ 3. mineru-kit parse {file_path} --format zip -o data/tmp/{doc_id}.zip --tier advanced
 ├─ 4. 解压到 data/parsed/{doc_id}/ , 扫描 *.md 与图片目录
 │      (适配层: 不假设固定文件名, 取最大的 .md 为主文档; 图片目录中的文件
 │       复制/保持为静态可访问路径, md内相对路径改写为 /static/parsed/{doc_id}/...)
 ├─ 5. 切片(chunk_service):
 │      - 按标题层级分段聚合, 目标 300~600字/块, 相邻块重叠约50字
 │      - 表格整体成块(chunk_type=table, 保md表格语法)
 │      - 每张图片独立成块(chunk_type=image, content=![](url),
 │        embed_text=图片前后的最近文本块约200字 + 所属标题)
 ├─ 6. embedding批量入库: embed_service 对全部 chunk 的 embed_text 向量化,
 │      BLOB写入 chunks.embedding; 回写 documents.description/page_count/chunk_count
 ├─ 7. status=completed → UPDATE + PUBLISH; 释放锁
 └─ 异常任意步骤: status=failed + error_msg → UPDATE + PUBLISH; 释放锁; ack
```

### 7.2 Embedding 抽象（services/embed_service.py）

```python
class EmbeddingProvider(Protocol):
    dim: int
    def embed(self, texts: list[str]) -> list[list[float]]: ...

class ApiEmbedding(EmbeddingProvider):   # OpenAI兼容 /v1/embeddings, 默认指向vLLM自部署(bge-m3)
class LocalEmbedding(EmbeddingProvider): # fastembed + bge-small-zh-v1.5 兜底
```

由 `.env` 的 `EMBEDDING_PROVIDER=api|local` 切换。**注意**：同一库内向量不可混用两个 provider（维度/空间不同），切换后需重新解析文档（提供 `python scripts/rebuild_vectors.py`，或界面重新解析）。API 调用带重试（3 次退避）与批量（每批 ≤ 32 条）。

### 7.3 RAG 问答流程（api/chat.py + services/rag_service.py）

```
POST /api/chat (multipart: session_id, content, image?)
 1. 落库 user 消息(图片存 data/chat_images/, 仅存image_path)
 2. query = content
    若带图 → 调 vision模型(deepseek-flash): 图片+问题 → 输出图片结构化描述,
             query = content + "\n[图片信息]" + 描述
 3. embedding(query) → 与内存向量矩阵做余弦相似度 → top3 chunks
 4. 相关性判断(文本模型): 输入 top3 的 (所属文档名+标题+前200字),
    要求输出 {"related": true|false, "reason": "..."} (JSON模式)
 5a. related → 上下文 = top3 chunks 的完整 markdown(图片块含 ![](/static/...) 链接)
     system: "你是知识库问答助手…回答基于以下知识库片段；片段中包含图片链接时,
              在合适位置用 markdown 图片语法原样引用该 URL, 禁止编造图片链接…"
     回答模型: 带图→deepseek-flash(图文+上下文) | 纯文本→deepseek-chat
 5b. not related → system: 自由回答, 禁止输出图片链接, 不提及知识库
 6. SSE 流式转发 token 到前端(event: token)
 7. 结束: assistant消息落库(content+meta={related, top3, model}), event: done
```

- **向量矩阵缓存**：API 进程启动时把全部 `chunks.embedding` 加载为 numpy 矩阵（`doc_id→chunk` 索引数组）；收到 SSE `doc_status=completed` 事件时增量刷新（重新查询该 doc 的向量插入缓存）。规模假设：≤5 万 chunk，内存 < 200MB，单次余弦 < 10ms。
- **图文混排实现**：知识库图片在上下文中以绝对 URL 的 markdown 图片语法存在，靠 system prompt 约束模型"原样引用、禁止编造"；前端 markdown-it 渲染即得图文混排效果。
- **不相关时**：模型自由回答，prompt 明确禁止编造图片。

### 7.4 SSE 通道设计（api/events.py + services/event_bus.py）

| 项 | 设计 |
|---|---|
| 端点 | `GET /api/events`（`text/event-stream`） |
| 事件类型 | `doc_status`（载荷：doc 摘要 JSON）、`ping`（每 25s 心跳，防代理超时） |
| 链路 | Worker `PUBLISH rag:events` → API 进程后台订阅任务 → 逐个推给本进程所有连接 |
| **一致性（竞态处理）** | 状态唯一权威源 = SQLite；SSE 只是通知。载荷带 `updated_at`，**前端仅接受比本地记录更新的消息**（丢弃乱序/过期）；EventSource 断线自动重连，**重连成功后强制拉一次分页列表**兜底漏推 |
| 降级 | Redis 不可用 → SSE 不可用，前端显示"实时刷新不可用"，保留手动刷新按钮；解析主流程不受影响 |

### 7.5 LLM 调用（services/llm_service.py）

统一 OpenAI 兼容 SDK（`openai` 包指向 DeepSeek base_url）：

| 用途 | 模型（.env 可改） | 输入 | 输出 |
|---|---|---|---|
| 回答（纯文本） | `deepseek-chat` | messages | stream |
| 回答（带图）/ 图片理解 | `deepseek-flash` | messages + image_url(base64) | stream / 文本 |
| 相关性判断 | `deepseek-chat` | prompt + JSON mode | `{related, reason}` |
| 查询向量化 | `EMBEDDING_MODEL`（待填） | text | float[] |

| DELETE | `/api/sessions/{id}` | - | 级联删除消息 |
| GET | `/api/sessions/{id}/messages` | - | `{items:[Message]}`（含 image URL / meta） |
| POST | `/api/chat` | multipart `session_id, content, image?` | SSE 流：`token` / `done{message_id, related}` / `error` |
| GET | `/static/**` | - | 静态图片（uploads 缩略不提供，parsed 图片 + chat_images） |

错误约定：非流式接口出错返回 `{detail}`（FastAPI 默认）；聊天 SSE 中出错发 `event: error` 后结束流，前端气泡展示错误并允许重发。

## 9. 前端设计

### 9.1 知识库页 `/kb`

```
┌────────────────────────────────────────────────────┐
│ [上传卡片: a-upload-dragger, 多选.pdf, 上传进度/结果提示]  │
├────────────────────────────────────────────────────┤
│ 状态筛选: a-radio-group(全部|待解析|解析中|解析完成|解析失败) │
│ ┌────────────────────────────────────────────────┐ │
│ │ 表格: 文件名 | 描述 | 大小 | 状态Tag | 切片数 |     │ │
│ │       上传时间 | 操作(重新解析†/删除)              │ │
│ │ 分页: a-pagination 每页10条                     │ │
│ └────────────────────────────────────────────────┘ │
└────────────────────────────────────────────────────┘   † 仅 failed/completed 显示
```

- **状态 Tag 颜色**：待解析=默认灰、解析中=蓝(带 loading 图标)、解析完成=绿、解析失败=红。
- **SSE**：页面挂载即连 `/api/events`；收到 `doc_status` 且 `updated_at` 新于本地 → 更新对应行（不在当前页/筛选条件下时仅更新总数与本地缓存）；断线重连后整页重新拉取。SSE 不可用显示"实时刷新不可用，请手动刷新"。
- **上传**：选完文件即上传（`POST /api/documents`），成功后把新记录插入列表第一页顶部；支持一次多选。

### 9.2 对话页 `/chat`

```
┌──────────┬──────────────────────────────────────┐
│ 会话列表   │  消息流                                │
│ [+新会话]  │   user气泡: 文本 + 图片缩略图(可点击放大)   │
│ 会话1(置顶)│   assistant气泡: markdown流式渲染(含图片) │
│ 会话2 ... │   ↑ 引用标注: 回答完毕展示"参考来源"      │
│ (悬停删除) │ ──────────────────────────────────── │
│          │  输入区: 多行文本框 + [附件按钮(选图+预览)]  │
│          │       + [发送(Enter发送/Shift+Enter换行)] │
└──────────┴──────────────────────────────────────┘
```

- 新会话默认创建一条"新会话"，首条提问后标题自动更新为前 20 字。
- 发送后 assistant 气泡即时出现并以打字机效果流式追加（fetch + ReadableStream 解析 SSE，EventSource 不支持 POST）。
- 回答完成（`done` 事件）后气泡下方展示"参考来源"（命中文档名 + 章节 + 相似度，来自 meta），以及"不相关，自由回答"标记。
- 切换会话拉取历史消息；删除会话需二次确认（Popconfirm）。

### 9.3 前端公共设计

- 路由：`vue-router`，`/kb` 默认页；全局状态：`pinia`（documents / chat / sse 三个 store，SSE 连接全局单例）。
- 请求封装：`fetch` + 统一错误提示（ant-design-vue 的 message）。
- Markdown 渲染：`markdown-it`（`html:false` 关闭透传防注入，图片走原生 `![]()` 语法），流式期间对增量内容整体重渲染（markdown-it 单次渲染毫秒级，可接受）。
- 类型定义集中在 `src/types`，与后端 schema 一一对应。
- vite dev 代理 `/api`、`/static` → `http://localhost:8000`。

## 12. 边界与异常处理

| 场景 | 处理 |
|---|---|
| Kafka 发送失败 | 文档置 failed（"投递队列失败"），可重试 |
| mineru-kit 超时/崩溃 | 杀子进程，failed + stderr 摘要（截断 500 字） |
| embedding 接口失败 | 单条重试 3 次退避，仍失败 → 整文档 failed |
| 同文档重复任务 | Redis 锁幂等，后者直接跳过 |
| SSE 断线 | EventSource 自动重连 + 重连后全量拉列表；chat 流中断则气泡标"生成中断"，可重发 |
| 删除解析中文档 | 允许删除：置删除标记，worker 完成后检测已删除则丢弃结果 |
| 聊天不带文本只带图 | 前端禁发；后端校验 content 非空 |
| 图片超过 10MB | 前端上传前拦截提示 |
