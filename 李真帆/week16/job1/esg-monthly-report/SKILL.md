# ESG 月报

为一家具名企业产出可直接交给客户的 ESG 月报。只收录时间窗内、能追溯到可靠来源的信息，按固定结构给出影响判断和行动建议。

## 确定输入

- 客户：从参数取，缺省为中国神华。
- 时间窗：从参数取。`YYYY-MM` 表示该自然月，`最近N天` 表示截至当天的 N 天；缺省为截至当天的最近 30 天。今天的日期以 `date +%F` 为准。
- 输出目录：`output/esg-monthly-report/<客户>_<起>_<止>/`，开工前先建好。
- 客户画像：客户是中国神华时读 `references/client-china-shenhua.md`；其他客户按 `references/search-playbook.md` 第 1 节先建画像。

## 工作流

### 1. 先列检索计划，再搜索

读 `references/search-playbook.md`，按"章节 × 信源 × 检索式"矩阵挑检索式：每个目标挑 1–2 条，总数不超过 24 条，给补搜留出余量。写入 `search_plan.md`（编号、章节、检索式、目标信源、执行结果）。计划写完之前不搜索。

### 2. 执行检索，逐条取证

逐条执行检索计划，把值得采信的结果写成证据卡。每完成一个章节的检索，就把该章的证据卡写进 `evidence.md`（章节多时可以按章拆成几个文件），不要把原文攒在上下文里。

```
### E01 | 标题
- 来源：发布机构（域名）｜一手 / 转载
- 发布日期：YYYY-MM-DD
- 日期依据：原文页面 / 搜索摘要
- URL：...
- 章节：政策 / 评级标准 / 行业 / 公司 / 对标
- 议题：E-碳排放 / S-职业健康安全 / G-合规 …
- 要点：
  - （3–5 条，保留数字、机构、文件名）
- 核实：已打开原文 / 仅搜索摘要
```

取证规则：

1. 只收时间窗内的信息。搜索结果里的相对日期（"3天前"）按今天换算成具体日期；日期无法确认的条目记入 `trace.md` 的"时间待核实"，不进正文。
2. 追溯一手来源。部委文件以部委官网为准，评级以评级机构或权威财经媒体为准，公司动态以公司官网和交易所公告为准；转载稿只用来找线索。
3. 同一事件的多个来源合并成一张卡，保留一手 URL。证据卡标题用页面原标题，不自己概括；一条事实对应一个链接，同一来源页支撑不了的内容不要写进去。
4. 打开原文核实（WebFetch）只留给进入正文的高价值条目，请求里写明要提取的内容。每次读取（包括栏目页和失败重试）都计入预算。读取失败时换一个来源再试一次，仍失败则标"仅搜索摘要"。
5. 检索式里不要用 `site:`，会让搜索报错。把站点名或机构名直接写进关键词。
6. 政策章节额外扫描 `references/search-playbook.md` 第 2.2 节的权威栏目页，挑出时间窗内的相关条目。
7. 挑读取对象时，优先权威媒体和部委官网的正文页。公告聚合页、PDF 附件、图片名单通常读不出内容，不要在它们上面花预算；需要这些内容时去找媒体写的文字稿。

预算：检索不超过 30 次，网页读取不超过 16 次。接近上限时先评估已有证据，再决定剩余检索式怎么取舍。

### 3. 筛选与定级

- 合并重复事件，剔除与 ESG 或与客户行业、议题无关的条目。剔除项连同理由记入 `trace.md`。
- 按 `references/analysis-frameworks.md` 第 6 节给每条定影响等级（高、中、低）。
- 各章采信条数参考目标：政策 5 条以上、评级标准 2 条以上、行业 5 条以上、公司 2 条以上、对标 3 条以上。不足时换关键词补搜一轮；仍不足就在报告里如实写"本期未检索到"。目标只是参考，不要用相关性低的条目凑数，不得编造。
- 把采信条目整理成 `sources.jsonl`，一行一条，按首次引用顺序编号：

```json
{"id":"S1","title":"...","publisher":"...","published":"2026-11-15","url":"...","section":"policy","verified":true}
```

`section` 取 policy、rating、industry、company、peer 之一；`verified` 表示是否打开过原文。

### 4. 分析

对每条高、中影响条目，按 `references/analysis-frameworks.md` 对应章节的框架写出"对客户的影响"和"建议"。对标企业汇总成一张行动表，并写出对客户的启示。

### 5. 成文

按 `references/report-template.md` 写 `report.md`：

- 结论先行，每章开头一句话说清本章最值得客户关注什么。
- 每个事实后面标注来源编号 `[S#]`，表格的来源列也一样写 `[S#]`。事实与判断分开，判断以"判断："开头。
- 数字只取自证据卡。拿不准的写"待核实"，不补全、不外推。
- 建议写成可执行的动作：谁做、何时做、做什么。
- 正文 2500–6000 字（表格文字计入），表格优先。

### 6. 交付前质检

逐项核对，结果写入 `trace.md`：

- 正文每个 `[S#]` 都能在 `sources.jsonl` 找到，`sources.jsonl` 每条都被正文引用。
- 每个 URL 都来自本次真实的检索或读取结果。
- 所有来源日期都在时间窗内。作为背景引用的旧资料单列在附录，不计入本期条数。
- 各章都有内容，或明确写了"本期未检索到"。
- 正文数字与证据卡一致。
- 报告头部写明时间窗、出具日期、检索条数、采信条数、主要局限。

`trace.md` 的结构：

```
## 过程统计
检索次数、网页读取次数、成功打开原文的条数
## 采信清单
| 编号 | 标题 | 章节 | 影响等级 | 核实方式 |
## 剔除清单
| 标题 | URL | 理由 |
## 时间待核实
## 质检结果
```

## 产物

```
<输出目录>/
├── report.md        月报（交付物）
├── sources.jsonl   来源清单
├── search_plan.md  检索计划与执行记录
├── evidence.md     证据卡
└── trace.md        统计、采信与剔除清单、质检结果
```

结束时向用户汇报：报告路径、采信条数、哪些章节证据偏少、哪些来源没能打开。

## 约束

只用内置搜索与网页读取工具取证，不编写抓取脚本。网页读取失败是常态，失败就换来源，不要对同一个地址反复重试。
